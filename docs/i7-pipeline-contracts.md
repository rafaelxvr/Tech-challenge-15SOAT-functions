# I7 pipeline source contracts and remaining activation

The source contract maps a push to `develop` to staging and a push to `main` to production. PRs, `pull_request_target`, tags, manual dispatch and other branches cannot pass `check-workflow-context.ps1`. CI verification identities remain read-only; no AWS OIDC identity or cloud deployment job is installed. APP's GHCR publishing is push-only and its Kind job is explicitly a local smoke test, not an AWS release.

`package-source.ps1` archives the reviewed Git tree with a fixed timestamp. Equal trees at different merge commits produce identical SHA-256 bytes; changed content requires staging again. Runtime image/JAR digest, contract version and migration version are separate required release-manifest fields. `start-deploy.ps1 -DryRun` validates artifact/manifest hashes, exact repository/environment executor/prefix, branch context, an open fresh cloud window and production's exact staged-source digest. Its result is explicitly `INPUTS_VALIDATED_DEPLOYMENT_DISABLED`; every live invocation and every `deploy.ps1 -ApplyReviewedPlan` invocation fails. These checks are not a signed promotion attestation and cannot authorize a cloud deployment.

The vendored cloud-window and lock scripts preserve the platform protocol: numeric allowance evidence or explicitly approved study-staging billing acknowledgment; fresh timestamps and closed-window rejection; conditional creation of `deployment-locks/shared-foundation.json` in the existing state bucket; ownership-only release and no stealing. Tests use the offline lock implementation and never acquire a real lock. Production can never use the study-staging billing acknowledgment.

`export-outputs.ps1` exports only the committed output allowlist and refuses sensitive allowlisted fields. APP's schema/bootstrap references are distinct environment/account Secrets Manager ARNs (no values); schema/view versions remain V8/V5/V7. FUN public JWK output rejects private parameters. Unknown password/state fields are dropped. Exported documents do not prove SQL privileges, key initialization or deployment success.

## External protections and activation prerequisites

Configure actual PR-only `main`/`develop` protections, required CI checks/review, restricted bypass, staging's develop-only environment policy and production's main-only policy before requesting deployment identity. Record repository identity/visibility, exact immutable OIDC subject, protection/ruleset IDs, required status check names, environment branch policies and reviewer settings as dated evidence. Workflow YAML cannot establish those controls and this change does not modify them.

APP still needs its separately reviewed cloud roots, migration/bootstrap Job and first-writer drain, compatible image rollout/rollback executor, ECR artifact binding and publisher. FUN still needs its reviewed single-owner runtime/auth-route state handoff and executor IAM review. Both need versioned artifact/config upload, exact platform-owned checksum bootstrap wiring, actual shared-lock integration, output receipt publication, terminal CodeBuild result propagation and verified immutable staging promotion receipt retrieval before any deployment job can be enabled. Do not substitute `promotedFromStaging=true` for that evidence. No eight-run R4 result is claimed.

The dependency order remains human state/OIDC bootstrap → foundation/private executors → platform/RDS → APP schema/roles/views → functions → stable Service/target binding and authorized APP routes/rollout → monitoring bindings. Actual cloud execution and production changes are outside this source task.

Local checks: `tests/source-package-contract.ps1`, `tests/workflow-context-contract.ps1`, `tests/cloud-window-tests.ps1`, `tests/release-guards-contract.ps1` and `tests/pipeline-contract.ps1`; FUN also runs `tests/verify-infrastructure.ps1`. Each repository owns its copied guard snapshot; security fixes must be propagated with its tests.
